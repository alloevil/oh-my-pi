## Failure evidence

With 26 CJK lark skills installed, the system-prompt `<skills>` listing alone
was 5584 of 20436 chars (~27% of every request); CJK ≈ 1 char/token, so
roughly 2–3k tokens per request, paid again by every subagent rendering its
own prompt.

## Root cause

The skills listing renders each skill's full multi-sentence description
unconditionally, regardless of task relevance; description length is
controlled by skill authors, not the harness.

## Targeted fix

`skills.promptDescriptionMode: "brief"` — render the frontmatter `summary`
(fallback: first sentence of the description) instead of the full description;
new `summary` frontmatter field for skill authors.

## Prediction

(Reconstructed. The skill-routing canary did not exist yet; routing was
checked by an ad-hoc offline A/B instead.)

- System prompt chars −20% (measured design target; cap-120 alternative was −15.7%).
- Skill-routing accuracy unaffected: top-1 skill selection on the offline
  eval set does not degrade vs full descriptions.

## Verification (manual, retroactive)

- Cost side: prompt 20436 → 16203 chars = **−20.7%** ✓ (beat the −20% bound).
- Quality side, strong router (fable-5, bare list): 52/52 both variants —
  masked the regression.
- Quality side, corrected method (weak router claude-haiku-4-5 + the real
  ~20k rendered prompt): brief 90.4% vs full 96.2% = **−5.8pp** ✗.
- Healing loop: hand-written discriminative summaries recovered brief to
  92.3% (indistinguishable from full's rerun noise), but summaries for all 26
  skills regrew the prompt to ~17.3k (−14%, near the plain cap), and the
  per-skill maintenance burden belongs to skill authors, not the harness.
