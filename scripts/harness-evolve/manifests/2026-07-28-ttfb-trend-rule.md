## Failure evidence

Session `019fac75-730d-7000-ab46-05190f8fb6b0` (user task: organize Mac Mail
by sender — a normal daily workload, not a dev session). 457 messages,
226 turns, single model. Measured from its `stage_timings` /
`outbound_summary` rows:

- outbound message payload grew 8K → 2.75M chars with no compaction;
- provider ttfb held ~10s median for ~200 turns, then the last 26 turns
  averaged 24s, one turn 47.6s, worst 164.7s — which tripped the stream-stall
  watchdog and produced the session's one ⚠ error turn;
- the user noticed the degradation by feel and reported the session id. The
  harness said nothing at any point.

This is the justifying incident the backlog item "context-health signals —
deferred pending a real incident" was waiting for.

## Root cause

Nothing watches latency trend. Stage timings are recorded per turn but only
read when a human runs `omp doctor --stages`. A session whose context grows
monotonically degrades ttfb gradually — each turn is only slightly worse than
the last, so there is no single anomalous event for existing guards
(provider-errors fires only after turns actually fail). The signal that
predicts the stall — recent-ttfb vs session-baseline ratio — is computable
from data we already persist.

## Targeted fix

Pure detector `detectTtfbTrend(ttfbMs: number[])` in `stages.ts`:

- needs ≥ 32 samples, else no verdict;
- `recent` = median of the last 12 samples, `baseline` = median of everything
  before them;
- **degraded** when `recent ≥ 2× baseline` AND `recent ≥ 5s` (the floor keeps
  fast sessions from flagging on harmless 200ms→500ms ratios), OR
  `recent ≥ 30s` outright (a session that starts slow has no healthy baseline
  but is still degraded);
- medians, not means — one 164s outlier must not move either window.

`scanSession` additionally collects the ttfb series (reusing
`parseStageTimingsRow`) and the last outbound `messageChars`; new doctor rule
`ttfb-trend` (warn) reports recent vs baseline, the ratio, and the outbound
payload size as the likely cause.

**Pull-mode only** per the incubation discipline: doctor rule now, no live
guard until the false-positive rate over real sessions is known. Promotion
path: wire the same detector into the turn-boundary guards once ≥2 weeks of
sessions show acceptable FP.

### Adjudication — prediction falsified, root cause corrected

The pre-registered trend prediction FAILED on replay: the detector never fired
on the mail session. Recomputing with medians (as the detector correctly does)
showed recent 12.7s vs baseline 10.0s — ratio 1.27, nowhere near 2×. The 2.4×
figure that motivated the card came from bucket *means*, which three terminal
outliers (164.8s, 164.5s, 47.6s) dominated. The incident's true signature:

- a **stall cluster** (4 turns ≥60s; the watchdog killed one, the user silently
  endured the rest — invisible to every existing rule), and
- **chronic broker slowness** (10.1s median from turn one, flat while the
  outbound payload grew 8K → 2.75M chars — prompt caching kept prompt
  processing constant; the "context growth ground the provider" causal story
  was wrong too).

Rule revised to report what the data supports: `ttfb-stalls` (warn),
`ttfb-trend` (warn, kept as the cheap early form — no real-world hit yet),
`ttfb-chronic` (info). Replay after revision: mail session → stalls warn
(4×, max 164.8s) + chronic info (10.1s/226 turns); negative control fired only
on the one session with real stall errors.

Meta-lesson recorded: the analyst preached medians and computed means. The
pre-registered replay is what caught it — exactly the failure mode the card
discipline exists for.
